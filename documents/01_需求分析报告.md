# 徐霞客时空游记系统 — 需求分析报告

**文档编号**：01  
**版本**：V1.0  
**编写日期**：2026-05-26  
**项目名称**：徐霞客时空游记系统（Xu Xiake Spatiotemporal Travel Journal System）

---

## 1. 项目概述

### 1.1 项目背景

徐霞客（1587—1641）是明代杰出的地理学家、旅行家和文学家，其代表作《徐霞客游记》系统记录了数十年间对山川地貌、风土人情、古迹文献的实地考察。本项目旨在构建一个**连接古今的旅游文化分享平台**：现代用户可注册账号、浏览与徐霞客足迹相关的景点与文献，在真实或虚拟景点进行「时空打卡」，并撰写可关联多个景点的游记，形成古今对话的数字化旅游文化社区。

### 1.2 建设目标

| 目标维度 | 具体描述 |
| -------- | -------- |
| 数据管理 | 对用户、景点、文献、游记及打卡关联进行结构化持久化存储 |
| 业务支撑 | 支持用户注册登录、景点浏览、文献查阅、游记发布与多景点打卡 |
| 关系建模 | 正确表达实体间 1:n 与 **m:n** 联系，尤其突出游记与景点的多对多关系 |
| 工程质量 | 满足关系型数据库规范化要求，为后续逻辑设计、物理实现与性能优化奠定基础 |

### 1.3 系统边界

- **系统内**：用户账号管理、景点与文献信息维护、游记发布、游记—景点打卡关联、基础查询与统计。
- **系统外**：第三方支付、地图导航、实时定位服务、内容审核与推荐算法等（本阶段不纳入核心数据模型，可作为扩展接口预留）。

## 2. 核心业务场景

### 2.1 用户注册与身份管理

现代游客通过平台注册个人账号，系统记录用户名、加密密码、头像路径、注册日期及个人简介。用户名在系统内须唯一，以保证登录与身份识别的准确性。用户注册后可维护个人资料，为后续发布游记提供主体身份。

**业务流程简述**：填写注册信息 → 校验用户名唯一性 → 密码加密存储 → 生成 `UserID` → 写入用户表。

### 2.2 景点信息浏览与徐霞客足迹标识

平台维护全国范围内的旅游景点库，每条记录包含景点名称、所属省份、开放时间、文字描述，以及**是否徐霞客曾游历**的标志位 `IsXuXiake`。用户可按省份、是否徐霞客足迹等条件筛选景点，为「古今同游」主题提供数据基础。

**业务流程简述**：用户进入景点列表 → 按省份/徐霞客足迹筛选 → 查看景点详情及关联文献。

### 2.3 古迹文献查阅

每个景点可关联零条或多条历史文献（如《徐霞客游记》原文片段、译注、成文年代等）。文献通过 `LocationID` 外键归属某一景点，体现 **Location : Literature = 1 : n** 的从属关系。用户在某景点详情页可阅读原文与译注，增强文化沉浸感。

**业务流程简述**：选定景点 → 加载该景点下全部文献 → 展示原文、译注与成文日期。

### 2.4 游记发布与互动

已注册用户可撰写游记，包含标题、正文、发布时间及点赞数。游记通过 `UserID` 外键归属发布者，体现 **User : Travelog = 1 : n** 关系。同一用户可发布多篇游记；删除用户时，其名下游记应级联删除（物理设计阶段实现）。

**业务流程简述**：用户登录 → 撰写标题与正文 → 系统记录 `PublishTime` → 生成 `TravelogID` → 游记入库。

### 2.5 时空打卡（游记—景点多对多）

**系统核心亮点**：一篇游记可记录作者在**多个景点**的打卡经历；同一景点也可出现在**多篇游记**的打卡记录中。二者之间为典型的 **m : n** 关系，必须通过桥表 `Travelog_Location` 拆解，并在桥表中记录每次打卡的 `CheckInTime`（时空打卡时间戳）。

**业务流程简述**：用户发布/编辑游记 → 选择本次游历涉及的一个或多个景点 → 为每个景点填写打卡时间 → 向桥表插入 `(TravelogID, LocationID, CheckInTime)` 组合记录。

### 2.6 典型查询场景（为后续索引设计埋伏笔）

| 场景编号 | 查询描述 | 涉及实体/字段 |
| -------- | -------- | ------------- |
| Q1 | 按用户名登录 | `User.Username` |
| Q2 | 查询某省全部徐霞客足迹景点 | `Location.Province`, `Location.IsXuXiake` |
| Q3 | 按发布时间倒序浏览最新游记 | `Travelog.PublishTime` |
| Q4 | 查询某篇游记打卡过的全部景点 | `Travelog_Location` 桥表 |
| Q5 | 统计某景点被多少篇游记打卡 | `Travelog_Location.LocationID` |

## 4. 非功能需求

| 类别 | 要求说明 |
| ---- | -------- |
| 数据一致性 | 所有外键引用必须有效；主键唯一、非空 |
| 安全性 | 用户密码不得以明文存储，须采用不可逆或加盐哈希（如 bcrypt） |
| 可扩展性 | 桥表设计便于未来扩展打卡备注、照片、经纬度等属性 |
| 性能 | 支持千级用户、万级游记与打卡记录的高效查询（依赖索引与范式化表结构） |
| 兼容性 | 目标数据库：MySQL 8.0+，字符集 UTF-8（`utf8mb4`） |

## 5. 数据字典（Data Dictionary）

以下五张逻辑表严格对应项目规定的五个核心实体，字段命名、语义与约束与课程设计预设保持一致。

### 5.1 用户表 `User`

| 字段名 | 中文名 | 数据类型 | 长度/精度 | 允许空 | 默认值 | 约束说明 |
| ------ | ------ | -------- | --------- | ------ | ------ | -------- |
| UserID | 用户编号 | INT | — | 否 | 自增 | **主键（PK）**；系统自动生成，唯一标识用户 |
| Username | 用户名 | VARCHAR | 50 | 否 | — | **唯一（UNIQUE）**；登录凭证，不可重复 |
| Password | 密码 | VARCHAR | 255 | 否 | — | 存储加密后的密码摘要（如 bcrypt），禁止明文 |
| AvatarPath | 头像路径 | VARCHAR | 255 | 是 | NULL | 相对或绝对 URL/文件路径，用于前端展示头像 |
| RegisterDate | 注册日期 | DATE | — | 否 | CURRENT_DATE | 用户完成注册的日期 |
| Bio | 个人简介 | TEXT | — | 是 | NULL | 用户自我介绍，建议不超过 500 字 |

**实体说明**：系统的操作主体。一条用户记录可对应多篇游记（1:n，在游记表中体现）。

---

### 5.2 景点表 `Location`

| 字段名 | 中文名 | 数据类型 | 长度/精度 | 允许空 | 默认值 | 约束说明 |
| ------ | ------ | -------- | --------- | ------ | ------ | -------- |
| LocationID | 景点编号 | INT | — | 否 | 自增 | **主键（PK）** |
| LocName | 景点名称 | VARCHAR | 100 | 否 | — | 景点官方或常用名称 |
| Province | 所属省份 | VARCHAR | 50 | 否 | — | 省级行政区名称，支持按省检索 |
| OpeningHours | 开放时间 | VARCHAR | 100 | 是 | NULL | 如「08:00—18:00」或「全天开放」 |
| IsXuXiake | 是否徐霞客足迹 | TINYINT(1) | — | 否 | 0 | **0=否，1=是**；标识该景点是否在徐霞客游记中有记载 |
| Description | 景点描述 | TEXT | — | 是 | NULL | 景点历史文化、地理特色等介绍 |

**实体说明**：旅游资源与文化载体。与文献为 1:n；与游记通过桥表为 m:n。

---

### 5.3 文献表 `Literature`

| 字段名 | 中文名 | 数据类型 | 长度/精度 | 允许空 | 默认值 | 约束说明 |
| ------ | ------ | -------- | --------- | ------ | ------ | -------- |
| LitID | 文献编号 | INT | — | 否 | 自增 | **主键（PK）** |
| LocationID | 所属景点 | INT | — | 否 | — | **外键（FK）** → `Location(LocationID)`；ON DELETE CASCADE |
| OriginalText | 原文内容 | TEXT | — | 否 | — | 古籍原文或摘录 |
| TranslateInfo | 译注信息 | TEXT | — | 是 | NULL | 现代汉语翻译或学术注释 |
| WriteDate | 成文年代 | VARCHAR | 30 | 是 | NULL | 如「崇祯九年」「1616年」等，兼容历史纪年 |

**实体说明**：从属于某一景点的文献资料。一个景点可有多条文献，一条文献仅归属一个景点（1:n）。

---

### 5.4 游记表 `Travelog`

| 字段名 | 中文名 | 数据类型 | 长度/精度 | 允许空 | 默认值 | 约束说明 |
| ------ | ------ | -------- | --------- | ------ | ------ | -------- |
| TravelogID | 游记编号 | INT | — | 否 | 自增 | **主键（PK）** |
| UserID | 发布用户 | INT | — | 否 | — | **外键（FK）** → `User(UserID)`；ON DELETE CASCADE |
| Title | 游记标题 | VARCHAR | 200 | 否 | — | 游记主题标题 |
| Content | 游记正文 | LONGTEXT | — | 否 | — | 支持较长篇幅的正文内容 |
| PublishTime | 发布时间 | DATETIME | — | 否 | CURRENT_TIMESTAMP | 精确到秒的发布时间，支持时间线排序 |
| Likes | 点赞数 | INT | — | 否 | 0 | 非负整数，≥ 0 |

**实体说明**：用户发布的游记主体。与景点通过桥表形成 m:n，打卡细节不冗余存入本表。

---

### 5.5 游记景点打卡关联表 `Travelog_Location`（桥表）

| 字段名 | 中文名 | 数据类型 | 长度/精度 | 允许空 | 默认值 | 约束说明 |
| ------ | ------ | -------- | --------- | ------ | ------ | -------- |
| TravelogID | 游记编号 | INT | — | 否 | — | **外键（FK）** → `Travelog(TravelogID)`；**联合主键组成部分**；ON DELETE CASCADE |
| LocationID | 景点编号 | INT | — | 否 | — | **外键（FK）** → `Location(LocationID)`；**联合主键组成部分**；ON DELETE CASCADE |
| CheckInTime | 打卡时间 | DATETIME | — | 否 | — | 用户在该景点对应的「时空打卡」时刻 |

**实体说明**：消解游记与景点之间的 m:n 联系。联合主键 `(TravelogID, LocationID)` 保证同一游记对同一景点仅一条打卡记录；不同游记打卡同一景点、或同一游记打卡不同景点，均通过多行桥表记录表达。

## 6. 实体联系概览（需求阶段）

| 联系 | 类型 | 参与实体 | 实现方式 |
| ---- | ---- | -------- | -------- |
| 用户 — 游记 | **1 : n** | User, Travelog | 游记表含 `UserID` 外键 |
| 景点 — 文献 | **1 : n** | Location, Literature | 文献表含 `LocationID` 外键 |
| 游记 — 景点 | **m : n** | Travelog, Location | 桥表 `Travelog_Location` |

## 8. 需求分析结论

本系统在业务上围绕「**用户写游记、景点承载文化、文献佐证历史、桥表记录多景点打卡**」四条主线展开。数据模型包含五个核心实体，其中 **游记与景点的 m:n 关系** 通过 `Travelog_Location` 桥表规范化表达，避免在游记表或景点表中产生重复组与冗余属性。后续概念结构设计将在 E-R 图中显式标注该多对多联系；逻辑结构设计将给出关系模式与 1NF/2NF/3NF 证明；物理设计将输出 MySQL DDL 与优化索引。
